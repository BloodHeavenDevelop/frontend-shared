## System Overview

`@bloodheaven/frontend-shared` v0.16.0 is a Nuxt layer consumed by the platform frontends through `extends`. It ships UI primitives, the `.hm-*` stylesheet, fonts, the theme registry and boot script, the reCAPTCHA composable, and the shared `/verify` and `/unsubscribe` pages.

**It holds no session logic.** A search of the snapshot found no `WebSocket`, `Authorization`, refresh, logout or auth-token storage code. Those live in each app (`stores/auth.store.ts`, `plugins/01.api.ts`, the WebSocket composable) and in the `auth-ui` layer, so they belong to each service's audit.

### Privileged Roles

None. The layer has no backend, role or credential. It runs with the privileges of the consuming app's origin, which is why an XSS here affects every consumer.

## Potential Risks

- **Tokens in query strings on `/verify` and `/unsubscribe`.** Both pages read `?token=` and POST it on mount. The token can remain in browser history and in proxy access logs. These are single-purpose tokens, and the pages load no third-party resource of their own.
- **Automatic action on page load.** `/unsubscribe` acts on mount without a confirmation click. A person who opens a forwarded link unsubscribes the original recipient. Mail scanners that execute JavaScript could do the same.
- **Inline boot script and future CSP.** The theme boot script is inline in every page's `<head>`. Its content is constant, but a strict CSP will need a hash or nonce for it.

## Findings

### Vulnerability Details

### [FS-01](../findings/FS-01-toast-renders-strings-as-html.md) - Toast Container Renders Plain Strings As HTML - High

**Description:** `useToasts().add()` is the notification API of every platform frontend. Its contract is `title: string` and `description?: string`, and nothing in the type or name says the value is HTML. `ToastsContainer.vue` nevertheless assigns both through `v-html`.
Neither `add()` nor `update()` in `components/ui/ToastsContainer/composables.ts` escapes or sanitises. Call sites pass entity names and backend messages. One confirmed chain in the deployer frontend, which mounts this container in `app.vue:33`:
1. `POST /api/cloudflare/credentials` and `PATCH /api/cloudflare/credentials/:credentialId` require `DashboardCreate`.
2. `ICredentialCreate.Name` has only `binding:"required"`. `Create` and the update path apply `strings.TrimSpace` and store the value, so markup survives. Creation needs a token Cloudflare accepts; a rename of an existing credential does not need a new one.
3. A second user with `DashboardCreate`, or a superAdmin, presses **Verify** on that credential.
4. The name is assigned to `innerHTML`. An event-handler payload such as `<img src=x onerror=...>` runs in the deployer origin.
5. The deployer keeps the access and refresh tokens in `localStorage` (`deployer/frontend/stores/auth.store.ts:94-95`), so the script can read and exfiltrate both.

**Assets:**
- `components/ui/ToastsContainer/ToastsContainer.vue` — toast `title` and `description` slots [https://github.com/BloodHeavenDevelop/frontend-shared]
- `components/ui/ToastsContainer/composables.ts` — `useToasts()` [https://github.com/BloodHeavenDevelop/frontend-shared]
- Confirmed call site: `deployer/frontend/pages/cloudflare/index.vue` — `onVerify()` [https://github.com/BloodHeavenDevelop/deployer]

**Status:** Pending Fix

**Classification**

| | |
|---|---|
| **Impact Rate** | 4/5 — account takeover through theft of access and refresh tokens |
| **Likelihood Rate** | 3/5 — the confirmed chain requires a privileged permission (`DashboardCreate`) |
| **Exploitability** | Semi-Dependent — needs the permission and a victim pressing Verify |
| **Complexity** | Simple |
| **Severity** | High (score 4×3=12) |

**Recommendations**

**Remediation:** 1. Render `title` and `description` as text (`{{ toast.title }}`) in `ToastsContainer.vue`, release a new `frontend-shared` version, and bump every consumer.
2. If a toast genuinely needs markup, add a separate slot or `customComponent` at that call site. Do not accept an HTML string in the general API.
3. Grep consumers for toast strings containing intended markup before release, since they would start showing literally.
4. Add a CSP at the platform proxy as defence in depth.

**Resolution:** —

**Evidences:** PoC, PoC code and results — see [FS-01](../findings/FS-01-toast-renders-strings-as-html.md#evidences).

## Appendix 3. Additional Valuables

### Unconfirmed Items

- None.

### Verified Controls

- `bh-theme` cookie: the value written is checked by `isThemeId`, and the boot script applies it only if it is in the constant theme list, so a cookie planted from a sibling subdomain cannot inject anything.
- Cookie attributes: `Path=/`, `SameSite=Lax`, `Secure` on HTTPS. It carries a preference only.
- `themeCookieDomain`: returns no domain for IPs and single-label hosts; browsers reject a public-suffix domain.
- Boot script: built from constants via `JSON.stringify`; decode errors are caught.
- reCAPTCHA loader: fixed Google origin, site key passed through `encodeURIComponent`.
- `/verify` and `/unsubscribe`: messages render by interpolation, and the POST target comes from runtime config rather than the URL.
- `v-html` occurs only in `ToastsContainer.vue` (FS-01). No `innerHTML`, `eval`, `postMessage` or `window.open` in layer components.
- No open-redirect helper exists in the layer. Link props are supplied by the app.
- Production dependency audit: 0 advisories.

### Dismissed Candidates

- **`bh-theme` on the parent domain:** no sensitive content and allowlisted on read.
- **`Math.random` toast ids:** UI keys, not security values.
- **Dev-dependency advisories** (`pnpm-_.json`: 3 critical, 28 high): build and dev tooling of this layer's own workspace. The layer ships source and declares peers, and the production audit is clean. Consumers' resolved versions are assessed in their audits.
- **`profileUrl` and `:to` props as open redirects:** values come from app code. No URL-derived value reaches them inside the layer.
